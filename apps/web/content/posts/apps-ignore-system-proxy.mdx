先说结论：macOS 的「系统代理」是一个**约定**，不是强制。

你在「系统设置 → 网络 → 代理」里填的地址，只是被写进了系统配置库里的几个键。
没有任何机制拦截流量、也没有任何机制要求程序去读它。读不读，全看那个程序的作者
当初选了哪套网络库、以及他有没有想起这回事。

所以「Clash 开着、系统代理也设了，但某个软件照样直连」不是配置错了，是那个软件
压根没打算看你的配置。知道它属于哪一类，才知道该怎么治。

## 谁会读，谁不会

会读的：用 macOS 自带网络栈的程序。Safari、以及绝大多数用 `URLSession` / CFNetwork
发请求的原生 app —— 这些库默认就会去查系统代理配置，作者什么都不用做。

不会读的，大致三类。

### 一、自带网络栈的图形程序

Electron 应用是最常见的一种，而且它的行为容易让人误判：**同一个 app 的两半可能不一样**。
渲染进程走 Chromium 的网络栈，Chromium 默认会读系统代理；但主进程里那些用 Node 的
`http` / `fetch` 发出去的请求，走的是 Node 的路子，只认 `HTTP_PROXY` / `HTTPS_PROXY`
这类环境变量。

于是你会看到很拧巴的现象：应用里点开的网页能加载，但它自己的登录、更新检查、
遥测上报全部超时。看起来像「一半走代理一半不走」，其实是两套网络栈各读各的配置。

游戏客户端和一些自己实现协议的专有软件更干脆 —— 它们连 HTTP 都不一定用，
系统代理这个概念对它们不存在。

### 二、命令行工具链

终端里的东西各有各的规矩，而且规矩不统一：

- `curl` 不读系统代理，只认 `http_proxy` / `https_proxy` 环境变量
- Go 写的程序默认走 `ProxyFromEnvironment`，同样只认环境变量
- `pip`、`npm`、`cargo` 各有各的配置文件，且它们的配置项和环境变量之间还有优先级关系

这就是「我明明 `export` 了 `https_proxy`，怎么还是不走」的来源：你导出的是**当前这个
shell** 的环境变量。新开一个终端标签、或者某个工具在子进程里把环境清理过一遍，
它就没了。

### 三、后台进程与守护进程

由 `launchd` 拉起来的东西不继承你 shell 里的任何环境变量 —— 你的 `.zshrc` 对它们
不存在。自动更新器、同步客户端、各种常驻的 agent 都属于这一类，而且它们通常
**根本没有让你填代理的地方**。

Docker Desktop 是这一类里最常被问到的：`docker pull` 的拉取动作实际发生在它自己的
那台虚拟机里，那个进程连你 macOS 上的设置都看不见，更谈不上读。

## 怎么判断手上这个属于哪一类

不用猜，两步就能分出来。

先在同一台机器上用浏览器访问同一个域名。浏览器通、目标程序不通，说明代理本身是好的，
问题在那个程序读不读配置。

再在终端里试：

```bash
https_proxy=http://127.0.0.1:7890 <你的命令>
```

加上环境变量就通了，说明它属于第二类（认环境变量）。加了还是不通，那它要么自带网络栈
不看环境变量，要么真正发请求的根本不是你启动的这个进程 —— 后者正是 Docker 那种情况。

## 三种解法，代价依次递增

**给它单独配代理。** 能配的就配：Docker Desktop 有自己的代理设置，`npm` 有
`.npmrc`，`git` 有 `http.proxy`。最省事，但只管这一个程序，而且下次换台机器要重来一遍。

**按进程接管。** 在系统网络层把指定进程的连接拦下来，按你的规则转发给你已经在跑的
上游。程序读不读系统代理不再重要 —— 它压根没有选择权。代价是要装一个系统扩展。
Appidge 做的就是这件事，它不提供任何节点，出口永远是你自己配的那个上游。

**上 TUN。** 建一块虚拟网卡把全机流量都接过去，什么都能管。代价也最实在：改路由表、
接管 DNS，和别的虚拟网卡容易打架，软件崩了整机断网。为了几个不听话的程序付这个代价，
多数时候不划算。
