如果你在 macOS 上打包时看到这一句：

```
A timestamp was expected but was not found
```

`xcodebuild archive` 或 `codesign` 随即失败 —— **先去看你的代理**。

这个故障在我们自己的发布流程里复发过三次。而且它有个额外的讽刺：
**我们做的就是代理转发工具，被拦住的正是我们自己的出包链路。**

## 为什么签名链路特别怕代理

签名时，`codesign` 会向 Apple 的时间戳服务发一个 RFC 3161 请求 ——
这是**同步**的：请求不回来，签名就完成不了。

同类的还有证书吊销检查（OCSP、CRL）和公证 API。它们的共同点是：

- **同步**，卡住就整条流程卡住
- **对延迟和抖动极端敏感**，超时窗口不宽
- **走代理毫无收益** —— 这些请求既不需要换出口，内容也不敏感

于是「配置过代理就默认走代理」这条对绝大多数流量都对的规则，在这几个域名上恰好是错的。
代理稍微一抖，`archive` 就有一半概率失败，而报错信息不会提代理一个字。

## 第二层：它有时不带域名

修完域名匹配之后，我们以为完了。没有。

**时间戳请求的连接有时只带 IP，不带域名。** Apple 有自己的 17/8 地址段，
这类连接直接就是往一个 IP 去的。只按域名匹配的排除规则，在这种连接上**完全不生效** ——
它从闸门旁边穿过去了。

所以域名闸之外还得补一道 IP 段闸。这一层是第二次复发才暴露出来的：
第一次修完看起来好了，其实只是那阵子的连接恰好带了域名。

## 第三层：系统那个服务不听你的

还有一个更难缠的：macOS 的 `XPCTimeStampingService`。

它**无视系统代理的例外名单**，而且维持着**跨天的 keep-alive 连接池** ——
你改了代理配置，它手里那条旧连接还在，照旧从旧路走。

结论是：出包窗口不只要把规则配对，还得**关掉系统代理并 `pkill -9` 掉这个服务**，
逼它重新建连。这一条在任何按进程分流的工具下都成立，不是某一家的问题。

## 我们最后怎么做的

把 Apple 签名与公证的基础设施域名做成**内置硬闸**：命中即强制直连，
**优先于用户写的任何规则**。

```
timestamp.apple.com        RFC 3161 时间戳
ocsp.apple.com             证书吊销状态
ocsp2.apple.com            现行系统主要访问的第二代端点
crl.apple.com              吊销列表下载
valid.apple.com            证书有效性验证
appstoreconnect.apple.com  notarytool 公证 API
```

两个刻意的设计决定：

**匹配是精确整串，不含子域、不做通配。** 列表收窄到「走代理必然有害」的那几个，
不加 S3/CDN 通配 —— 否则会误伤用户真正想代理的 Apple 域名（比如 `www.apple.com`）。

**它是硬闸，用户规则盖不住。** 就算你写了 `*.apple.com → 走代理`，这几个域名照旧直连。
一般来说「用户规则最大」是对的，但这里的代价不对称：拦错了只是丢一点点「让签名走代理」
的自由，不拦则是打包随机失败还查不出原因。

## 你可以直接拿去用的

不管你用的是哪家工具：

1. 把上面那六个域名加进**直连**规则（或代理软件的例外名单）
2. 出包前关掉系统代理，并 `pkill -9 XPCTimeStampingService`
3. 如果修完仍偶发，检查你的规则是否**只按域名匹配** —— 补一条 Apple 的 17/8 段直连

第 3 条是最容易漏的，也是我们付出最多次失败才找到的那一条。
