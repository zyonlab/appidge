`docker pull` 卡住，和前两篇讲的都不一样：这次连**发请求的进程都不在你这台 Mac 上**。

Docker Desktop 在 macOS 上跑着一台 Linux 虚拟机，守护进程在那台虚拟机里。
你敲的 `docker pull` 只是把命令递给它，真正去连 registry 的是虚拟机里的那个守护进程。
它看不见你的 `~/.zshrc`，看不见系统设置，也看不见你给终端配的任何东西。

所以「我环境变量都配了怎么还是不行」在这里是必然的 —— 那些配置的作用范围里
根本不包含它。

## 三个具体的坑

### 一、`127.0.0.1` 在虚拟机里不是你的 Mac

这是最常踩的一个。你的代理监听在 macOS 的 `127.0.0.1:7890`，于是你在 Docker Desktop
的代理设置里也填 `http://127.0.0.1:7890` —— 然后发现没用。

因为那个设置是给**虚拟机里的守护进程**用的，它眼中的 `127.0.0.1` 是虚拟机自己。
你的代理不在那里。要指回宿主机得用 `host.docker.internal` 这个专门的名字。

同样的道理也适用于容器内部：容器里的 `localhost` 是容器自己，不是你的 Mac，
也不是虚拟机。

### 二、三个「代理」是三件不同的事

Docker 语境里「配代理」至少指三件事，配错地方不会有任何提示：

| 你想让谁走代理 | 配哪里 |
| --- | --- |
| `docker pull` / `docker push` 拉推镜像 | Docker Desktop 的代理设置（作用于守护进程） |
| 已经跑起来的容器里的程序 | 容器的环境变量，或 `~/.docker/config.json` 里给容器注入 |
| `docker build` 过程中的 `RUN apt-get …` | 构建参数 `--build-arg HTTP_PROXY=…` |

构建那一栏最容易忽略：构建过程发生在临时容器里，**不继承你 shell 的环境变量**，
也不自动继承守护进程的代理设置。镜像拉得下来、`RUN` 里装包却超时，通常就是这个。

### 三、改完设置要让守护进程真的重启

Docker Desktop 的代理设置改完需要重启守护进程才生效。点了「Apply」之后没等它真的
重起来就急着重试，会得到一个和改之前一模一样的失败，然后误判成「设置没用」。

## 先搞清楚是谁在发请求

与其猜，不如看。拉镜像的时候看一眼当前有哪些进程在建立连接 —— Docker 的虚拟机
辅助进程会明明白白出现在那里，而它的名字取决于你装的是哪个版本，所以**看比记靠谱**。

这也是我们做活动页的原因：它实时列出正在联网的进程，点进去就能当场给它定规则。
不用先知道进程叫什么，才能治它。

如果你用的是 colima、OrbStack 或 podman，架构是一样的 —— 都是一台虚拟机加一个
守护进程，只是虚拟机的实现和设置界面不同。上面三个坑照样适用。

## 解法与代价

**用 Docker 自己的设置。** 三个地方分别配对。能解决问题，缺点是配置散在三处，
换台机器要重来，而且每次只覆盖 Docker 一家。

**按进程接管虚拟机辅助进程。** 把那个真正发请求的进程的连接拦下来，按规则转发给
你已经在跑的上游 —— 不用管 Docker 内部有几层配置。
[Appidge](/zh/) 做的是这件事，它不带任何节点，
出口仍然是你自己配的上游。代价是要装一个系统扩展。

**上 TUN。** 全机流量都走虚拟网卡，虚拟机的流量自然也在内。代价一样：改路由表、
接管 DNS，崩了整机断网；而且容器网络本身也用虚拟网卡，两者叠在一起更难排查。
