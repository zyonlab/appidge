按进程分流的难点从来不是「怎么写规则」，是**先搞清楚该给谁写**。

进程名不一定等于你认识的那个软件名，真正发请求的也常常不是你启动的那个进程
（[Docker 就是典型](/zh/blog/writing/docker-pull-proxy/)）。所以工作流是反过来的：
**先看它在连谁，再决定它该往哪走。**

## 活动页的五列

| 列 | 看什么 |
| --- | --- |
| Apps | 哪个进程。同一个 App 拉起的子进程会各自出现，这正是你要的粒度 |
| Destination | 它在连的目的地。判断「这条连接该不该走代理」主要看这里 |
| Rule | 这条连接**当前**命中的规则：Direct、Proxy、Block |
| Sent / Received | 收发字节。用来区分「真的在传数据」和「连上了但没动静」 |

连接还有 **Active** 和 **Closed** 两种状态。排障时别只盯 Active —— 超时失败的连接
往往一闪而过就变 Closed，把「只看活跃」的过滤关掉才看得到它。

## 典型用法：让它先犯错，再抓现行

不用提前想好规则。让那个连不上的软件跑起来，去活动页找它：

1. 触发一次失败的操作（拉取、登录、检查更新）
2. 在活动页按进程名或目的地找到那几条连接
3. 看 Rule 列 —— 如果是 Direct，那它现在就是在直连，超时也就不奇怪
4. 点进去，改成 Proxy
5. **不用重启目标程序**，规则即时生效，重试一次即可

这个顺序的好处是你**不必先知道进程叫什么**。名字是它自己报给你的，不是你猜的。

## 为什么是「新的盖旧的」，不是「更具体的赢」

规则页按时间倒序排列，同类规则里**较新的那条覆盖较早的**，被盖住的那条会显示成
「已覆盖」而不是消失。

很多工具用的是另一套：谁更具体谁优先。那套在配置文件里写规则时是对的 ——
你一次性想清楚整个规则集，具体的自然该赢。

但活动页的工作方式不是「一次想清楚」，是**边看边改**。你在排一个故障，试了 Proxy
不行、改成 Direct，又发现某个域名要单独放行。如果按「更具体的赢」，你每改一次都得
先回头确认有没有一条更具体的旧规则压着你 —— 那就把「点一下改掉」变成了「先做一次
规则审计」。

按时间倒序意味着**你最后做的那个决定一定生效**。这跟人的直觉一致：我刚改的就该算数。

被盖住的规则保留成「已覆盖」而不是删掉，是同一个道理的另一半：你能看见自己改过什么，
需要时可以回溯，但不必为了让新规则生效而先去清理旧的。

## 先粗后细，不用回头删

这两条性质合起来，给出一个很省事的用法：

先给整个进程写一条粗的（比如全部走代理），跑一阵子；发现某个目的地不该走代理，
再补一条更具体的。新规则在后，自动生效，旧的那条留在列表里标成已覆盖。

不需要在动手前把规则集设计对 —— 这本来也设计不对，因为你还没看见它到底在连什么。
