在 macOS 上拦流量有两个层可选：**socket 层**（拿到的是一条条「流」，附带发起它的进程）
和**包层**（拿到的是一个个 IP 包，通过一块虚拟网卡）。

TUN 类工具在包层。透明代理类的系统扩展在 socket 层。

如果你要做的是**按进程分流**，这个选择几乎是被决定的 —— 因为**进程身份只在 socket 层
是现成的**。

## 归因：现成的 vs 事后反查

socket 层拿到一条流的时候，系统连同流一起交给你的还有发起它的进程标识
（签名标识 / PID）。这是**连接建立前**就确定的元数据，不需要推断。

包层拿到的是 IP 包。包头里有源 IP、源端口、目的 IP、目的端口 —— **没有进程**。
想知道是谁发的，只能拿四元组去反查系统的连接表。

这个反查有两个问题：

- **短连接会漏。** 一次快速的请求可能在你反查之前就已经关掉了，连接表里查无此项，
  归因失败
- **失败是静默的。** 查不到就只能按默认规则处理，而你不会收到任何提示 ——
  表现是「规则偶尔不生效」，而且无法复现

对「按进程」这件事来说，一个偶尔归错的机制是很难用的：你没法判断是规则写错了，
还是这次没归对。

## 代价：socket 层拿不到什么

诚实地说另一半。

**不经过 socket 的流量它管不了。** 内核自己发的、某些底层协议、以及绕开常规
socket API 的东西，都不在这一层出现。要「全都管」的场景，包层才是对的。

**UDP 要单独考虑。** socket 层能拿到 UDP 流，但转发它有个硬约束：HTTP CONNECT
不能代理 UDP，只有 SOCKS5 的 UDP ASSOCIATE 能。所以「走代理的进程，它的 QUIC 怎么办」
必须显式回答，而不是自动就对了（我们默认拦掉逼它回落 TCP，也可以放行直连或真的走
SOCKS5，[取舍在这里](/zh/blog/writing/proxifier-alternative/)）。

包层没有这个问题 —— 它眼里 UDP 和 TCP 都只是包。这是包层实打实的优势。

## 崩了会怎样：这条是架构决定的，不是实现质量决定的

TUN 的工作方式是建一块虚拟网卡，把默认路由指过去。**路由指过去之后，那条路就是唯一的路。**
进程崩了、没来得及恢复路由表，流量就没地方去了 —— 整机断网。

socket 层不改路由表、不建虚拟网卡、不接管 DNS。扩展挂掉，流量按原来的路直连出去。
最坏的结果是「没分流」，不是「没网」。

这不是谁写得更仔细的问题，是两种架构各自的失败模式。选之前想清楚你更能接受哪一种。

## 那 TUN 什么时候才是对的

不是所有场景都该选 socket 层：

- 你要的是**全机接管**，包括那些不经过 socket 的流量
- 你依赖 fake-ip 那一套（在包层做域名映射，绕开本地 DNS 解析）
- 你不需要按进程区分 —— 全都走同一个出口，那归因精度就不重要了

反过来，如果你的诉求是「让这几个不听话的程序归我的规则管」，那你要的是精确归因，
socket 层更合适。

**这两者不该同时开着** —— 两个整机接管层会抢同一份流量，典型结果是断网，
[判别和恢复方法在这里](/zh/blog/writing/tun-conflict/)。
