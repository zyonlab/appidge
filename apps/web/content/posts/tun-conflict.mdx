## 为什么会断

TUN 的做法是建一块虚拟网卡（macOS 上叫 `utunN`），再改路由表，把默认路由指过去。
从此所有流量都先进这块网卡。

按进程接管走的是另一条路：在系统网络层按进程把连接拦下来转发，**不建虚拟网卡、
不改路由表、不接管 DNS**。

两者单独用都自洽。叠在一起就出事，最常见的死法是 DNS：一层把域名查询交给自己的
解析器，另一层又想把这条查询按规则转走，查询进了对方的虚拟网卡出不来。
域名解析不出来，上层看到的就是「什么都打不开」，但底层 IP 直连还通 ——
这正是「`ping` 得通、网页打不开」的来源。

## 怎么确认是不是这个问题

三条命令，不用猜。

看有没有多余的虚拟网卡：

```bash
ifconfig | grep -A 3 utun
```

看默认路由被谁拿走了：

```bash
netstat -rn -f inet | head
```

`default` 那一行如果指向某个 `utun`，说明有 TUN 类工具正在接管全机流量。

看 DNS 被交给了谁：

```bash
scutil --dns | head -30
```

如果 `nameserver` 指向一个本地回环地址或某个 `utun`，就是被接管了。

## 正确的分工

把两件事分开，各干各的：

- **代理客户端**（Clash / Surge / xray 之类）负责**出口**：节点、订阅、规则组、延迟测试。
  只保留本地监听端口，比如 `127.0.0.1:7890`。
- **按进程接管的工具**负责**接管与分流**：哪个进程走直连、哪个转给上面那个端口、
  哪个直接拦掉。

Appidge 就是按这个分工设计的：它不提供任何节点，出口永远是你自己配的那个上游。
把代理客户端的本地端口加成上游即可，订阅和节点照旧由它管，两边互不打架。
官网 [常见问题](/zh/#faq) 里也是同一套说法。

## 其他会打架的东西

不只是 Clash 系的 TUN。凡是会建虚拟网卡、抢默认路由的都算：

- 公司的 VPN 客户端（很多在连接期间会独占默认路由）
- 另一个也开着 TUN 的代理工具
- 部分虚拟机/容器软件的网络模式

同一时刻只让一个东西持有默认路由，是最省心的原则。

## 断网了怎么恢复

先关 TUN（或直接退出那个开了 TUN 的软件），路由表通常会自己恢复。还不行就把
Wi-Fi 关掉再开，逼系统重新拿一遍网络配置。

顺带说一句设计取舍：Appidge 的扩展是 fail-open 的 —— 它自己挂了，流量按原样直连，
不会把你的网络一起带走。这是选择透明代理而不是 TUN 的直接好处，代价是它管不了
不经过 socket 的流量。**没有免费的接管**，只有你更能接受哪一种代价。
