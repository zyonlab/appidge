# 营销自动化引擎设计——五步闭环

> 目标：把线上营销从「一个人 8h/天」压缩到「AI 跑体力活 + 人做判断 2–3h/天」。
> 铁律：发布动作永远人工执行；AI 只负责发现、筛选、起草、统计。

```
┌─────────────────────────────────────────────────┐
│  ① 产品定位 / 人群画像  ←──────────────┐        │
│         ↓ (产出评分标准与红线)          │        │
│  ② 线索发现（人群在哪）  ←──────┐      │ ⑤ 校准回路
│         ↓ (线索池)              │      │        │
│  ③ 分渠道管道执行               │ ④ 扩张回路    │
│         ↓ (动作日志)            │      │        │
│  ④ 执行中捕获新线索 ────────────┘      │        │
│         ↓                               │        │
│  ⑤ 效果统计与归因 ─────────────────────┘        │
└─────────────────────────────────────────────────┘
```

---

## ① 产品定位与人群画像

**输入：** 产品事实（功能、价格、红线）、已有用户反馈、竞品。
**产出（机器可用，不是一篇文档）：**
- 画像卡：人群特征、典型报错场景、聚集地假设
- **线索评分标准**：后面 ②④ 全靠它打分（痛点相关度 / 可回答性 / 版规风险 / 红线冲突）
- 红线清单：非 VPN、不提翻墙、不碰机场——作为所有草稿的硬校验规则

Appidge 版已完成，见 `docs/marketing-plan.md` §1–2。此步产出变更时（⑤反馈触发），下游评分标准同步更新。

## ② 线索发现——线索要分三类，处理方式不同

| 线索类型 | 例子 | 发现方式 | 进入哪种管道 |
|---|---|---|---|
| **渠道级**（社区/平台） | Linux.do、NodeSeek | 顺着搜索/竞品/referrer 找 | 评估后进社区矩阵 |
| **内容级**（帖子/关键词） | 「docker 不走代理」新求助帖 | API/RSS/搜索定时抓取 | 答题管道的每日队列 |
| **人级**（KOL/活跃用户） | 转发过 Clash Verge 测评的博主 | 顺着人找、互动记录 | 单独的关系管道，慢养 |

**线索池 schema（一张表贯穿全系统）：**
`lead(id, type, source, url, 摘要, 评分, 状态[新/排队/已处理/已转化/丢弃], 发现时间, 来源线索id)`
——`来源线索id` 是第④步扩张回路的关键：能回答「这条线索是哪条老线索裂变出来的」。

## ③ 分渠道管道——五种管道模板，不是一渠道一套代码

| 管道模板 | 适用渠道 | 自动化部分 | 人工部分 |
|---|---|---|---|
| **答题管道** | V2EX / Linux.do / NodeSeek / Reddit | 抓帖→打分→起草回复→进审核队列 | 改稿、亲手发布 |
| **内容管道** | 官网 SEO 博客 / 投稿 | 选题建议、初稿、关键词调研 | 核心踩坑细节人写、定稿 |
| **实时管道** | Telegram 群 | 关键词监听→提醒 | 人直接回（群里不发 AI 稿）|
| **事件管道** | HN / PH / 周刊投稿 | 材料准备、发布 checklist | 发布与互动全人工 |
| **关系管道** | 人级线索（KOL）| 动态跟踪、互动时机提醒 | 所有互动人工 |

每条管道的产出统一为**每日审核清单**：线索 + 草稿 + 风险标注 + 建议动作，人在一个固定时段批量处理。

## ④ 扩张回路——每次执行同时是一次侦察

管道执行时强制带一个「线索提取」后处理步骤，从处理过的内容里抽取：

- 帖子里提到的其他社区/工具/群组 → 渠道级候选
- 回复区反复出现的新报错场景 → 内容级选题 + 新监测关键词
- 高质量追问的用户、被多次引用的博主 → 人级候选
- 官网 referrer 里冒出的新域名 → 渠道级候选

抽到的候选写回线索池（状态=新，记录来源线索id），周四勘探槽人工评估。**这一步不做，系统三个月后就只会在最初三个社区里打转。**

## ⑤ 效果统计与反向迭代——最难的一步，先想清楚归因

低客单价（$3.99）+ 论坛场景的归因难点：回复里挂 UTM 长链接一眼广告味。可行手段（组合使用）：

1. **分渠道落地路径**：不同社区用不同短路径（如 appidge.com/v2、/ld），服务端日志天然分渠道，肉眼无感
2. **结账/首启一道题**：「从哪里知道 Appidge？」单选，自报归因兜底
3. **品牌词搜索量**：Search Console 里 "appidge" 查询量的周变化，衡量社区在场的间接效果
4. **周漏斗**：各渠道进站 → 下载 → 付费，写进社区台账

**反馈的三个去向：**
- → ②：进站为零的渠道降级，referrer 异军突起的升级（重排社区矩阵权重）
- → ③：哪类草稿模板转化好、哪类被社区冷遇，调 prompt 和内容结构
- → ①：如果付费用户画像和假设不符（比如英文用户占比意外高），修画像卡，全链路评分标准随之更新

## 落地顺序（每步都可独立验证）

1. **线索池 + 答题管道的监测层**（V2EX API / HN Algolia / Google 定时抓取 → 每日清单，先不写草稿）——跑两周看命中率：每天 ≥3 条高分线索才继续
2. 加**起草层**（评分标准 + 红线校验 + 草稿模板）
3. 加**⑤统计层**（短路径 + 周漏斗自动日报）
4. 加**④提取层**（后处理抽新线索回写）
5. 最后把 ① 模板化成通用 `marketing-planner` skill（换产品可复用）

## 两个最容易做塌的地方

- **④做成自由发挥**：「思考可能的新线索」必须是结构化提取字段（提到的社区/工具/人/关键词），否则 AI 每天产出一堆不可执行的感想。
- **⑤只统计不回写**：数据报表如果不落回线索池的评分权重和管道 prompt，闭环就断了——报表要的不是好看，是每周五复盘时能直接回答「下周砍哪个渠道、加哪个」。
