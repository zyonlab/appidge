# Network Extension 转发类应用实战经验

## 架构选型（做对了后面全省）

- 按进程分流选 **NETransparentProxyProvider（socket 层 flow）**，不选 TUN（包层）：flow 的
  进程签名/PID 是系统在连接建立前给的元数据，归因精确；TUN 只能拿裸 IP 包事后反查连接表，
  短连接/UDP 归因经常失败且静默。TUN 系的 fake-ip 污染、路由劫持、崩溃断网，这套架构天然没有。
- **fail-open 是底线**：扩展死了流量按原路走，最坏是「没分流」不是「没网」。授权服务故障、
  引擎异常都不允许升级成系统级断网。
- 回环流量**到不了** transparent proxy provider（平台行为，实测 0 命中）——防御代码可留，
  但别把功能建立在拦 loopback 上。
- 数据面热路径禁止 per-chunk I/O；UI 常驻动画（symbolEffect `.repeat(.continuous)`）在
  ProMotion 屏会吃满一个核。

## 防环与自我排除（转发类产品的命门）

- **本地代理（用户的 Clash/xray/mihomo）是全系统流量的汇聚点，绝不能接管，只能观测登记**。
  「接管+直连」= 全系统代理吞吐在你的扩展里二次读写——同根因事故连出三次才形成的铁律。
- 排除信号要**三路并用**：签名标识 + 可执行路径 + 「是否在本 app bundle 内」。未签名 CLI 的
  签名标识统一报 `a.out`，按标识排除会连坐所有未签名程序，必须回退到路径匹配。
- **本地代理身份要周期性重发现**（挂心跳），不能只在配置变更时查一次：用户换代理软件
  （xray → mihomo）不会改你这边的 `127.0.0.1:7890` 配置，但监听者已换人。
- **Apple 签名基础设施必须硬直连、优先级高于用户规则**：时间戳/OCSP/公证域名走抖动代理会让
  开发者自己 archive 半数失败。注意时间戳 flow 有时**只带 IP 不带域名**（Apple 自有 17/8 段、
  端口 80），纯域名匹配会穿闸，要补 IP 段闸。
- 环检测的自愈结果（学到的排除项）要**立即落盘**，不能只挂在切后台存盘上——崩溃/重启会把
  学到的排除清零、真环重开。

## 系统扩展升级（最深的坑：三种病）

macOS 按 (marketing, build) 元组决定是否替换系统扩展；替换窗口就是竞态窗口。

1. **会话绑死旧 provider（全系统黑洞）**：会话绑在已终止的旧 provider 上，拦流量却转发不了。
   修法是状态机：「运行版本≠包内版本」只记标志；「变回匹配」才重绑一次；持续不匹配超时
   （~8s）后做一次**有界**重启破死锁。「启动时无条件 restart」会绑得更早、黑洞更严重。
2. **XPC 监听器注册竞态**：换血窗口里新进程的 `NSXPCListener` **静默**注册失败（API 无错误
   回调），旧 job「等重启卸载」态占死固定 mach 名。根治 = **mach 服务名带扩展版本号**（新旧
   进程名字空间隔离）+ 扩展进程内自探活、仅 sessionless 时 exit 重生（有会话时杀进程 =
   全系统断网）+ app 侧候选名轮换。
3. **激活请求悬挂**：新 app 启动只探状态、`activate()` 被异步条件门住而从未提交 → 系统永不
   替换旧扩展。教训：激活请求**幂等提交、门槛条件越少越好**；所有「重启接管」入口顺带补一次
   activate。诊断口诀：`systemextensionsctl list` 没有新版本条目 + 日志只有 probe 没有
   "submitted activation request" = 悬挂。

根本缓解：**扩展版本与 app build 解耦**——扩展内容（Extension 目录 + 其依赖包）没变就不
bump 扩展版本，系统跳过替换，竞态窗口根本不打开；配指纹闸门双向硬失败（改了没 bump /
没改乱 bump）。

其他实测：密集出包会积累「waiting to uninstall on reboot」的扩展坟场，只有重启电脑能清；
升级验证用 `curl -m3` 逐秒探网 + 查连接日志有真实 flow，别只看 UI。

## 与 TUN 系软件共存（真实用户环境）

- 用户大概率装着 Clash 系客户端且开着 TUN/虚拟网卡/增强模式。**两个全接管层叠加 = 抢流量 +
  DNS 被截进对方虚拟网卡黑洞 = 断网**，且用户会归咎于最后安装的软件（你）。
- 对策三层：产品内探测 `utun*` 网卡并在接管开启时警示（可忽略，正经 VPN 也是 utun）；
  官网下载区放警示；FAQ 第一条回答「能不能同时开 TUN」——话术要点：关 TUN 不影响节点/订阅，
  只保留本地端口当上游即可。
- 排障先分清「谁在接管」：app 退出 ≠ 扩展没在拦（系统扩展进程由 launchd 常驻；用
  `log stream` 看有没有 flow 处理日志）。对方软件自身的断网（机场订阅普遍缺完整 dns 段，
  规则模式靠 CN 直连兜住、全局+TUN 就断网）也会赖到你头上——用对照实验归因，别急着修。
